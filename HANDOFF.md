# JOTL Handoff — 2026-02-24

## What JOTL is

Common Lisp implementation of the JAM protocol STF (State Transition Function)
as specified in Gray Paper v0.7.2. ~12K lines Lisp, ~1K lines Rust (crypto FFI).

Architecture: **let-over-lambda closures** — each of the 17 state components
(τ η κ λ β ψ ρ ι γ α ϕ δ π χ ω ξ θ) is a closure generated by the
`define-state-closure` macro. σ (sigma) is a pure byte store. Υ (upsilon)
orchestrates the 4-wave dependency graph. No CLOS, no mutation.

## Current status

### Passing

- **1000/1000 static test vectors** — byte-exact state root match on all 8 traces
  (fallback, safrole, storage, storage_light, preimages, preimages_light,
  fuzzy_light, fuzzy). Run: `bash scripts/test.sh`

- **Minifuzz no_forks: 102/102** — Full fuzz-v1 protocol compliance without forks.

- **Minifuzz forks: 51/102** — Passes 51 pairs, fails at pair 52 with state root
  divergence (block accepted by both sides, different output state).

### VRF status (fully enabled)

Bandersnatch IETF VRF is **fully enabled** for seal and entropy verification.
The root cause of earlier failures was that `ark-vrf`'s `verify(k, c, m, x)`
requires the `m` (additional data) parameter to be identical between prove/verify.

Key parameters per GP equations:

| Check | Key | VRF input | ad (additional data) |
|-------|-----|-----------|---------------------|
| Seal fallback (6.16) | `γ'S[HT mod E]` | `XF ⌢ η'₃` | `EU(H)` |
| Seal tickets (6.15) | `κ'[HI].kb` | `XT ⌢ η'₃ ⌢ ie` | `EU(H)` |
| Entropy (6.17) | Same as seal key | `XE ⌢ Y(HS)` | `[]` (empty) |

Where `EU(H)` = header serialization without the seal (`:save-unsealed` message
on header closure). Context tags: `XF = "jam_fallback_seal"`, `XT = "jam_ticket_seal"`,
`XE = "jam_entropy"`.

Rust FFI: `bandersnatch_verify_vrf(pk, input, input_len, output, proof, proof_len, ad, ad_len)`
Lisp: `(jam.ffi:bandersnatch-verify-vrf key input output proof &optional ad)`

### Known issue: forks pair 52 state root divergence

The block at pair 52 builds on the state produced by pair 48 (HP=0x2d48d236...,
parent SR=0xa183c085...). Both sides accept the block but compute different
state roots. The block is 1886 bytes (non-trivial extrinsics). All 51 previous
pairs match byte-exactly.

Not caused by:
- State GC (tested with 200 max states, same failure)
- VRF verification (block is accepted, not rejected)
- Preimage validation (block has no preimage errors)

Likely cause: a subtle STF edge case in one of the extrinsics that only triggers
in the forks scenario's specific state progression.

### Preimage validation

`integrate-preimages` in `delta.lisp` now properly signals `preimages-error`
when a preimage is not required (service doesn't exist, lookup entry absent,
or status list has odd length). Previously it silently skipped invalid preimages.

## How to run

```bash
# Build crypto FFI
cargo build --manifest-path crypto/jam-crypto/Cargo.toml --release

# Run all 1000 static tests
bash scripts/test.sh

# Run fuzzer target
bash scripts/fuzz-target.sh /tmp/jam_target.sock

# Run minifuzz (in separate terminal)
cd jam-conformance/fuzz-proto
python minifuzz/minifuzz.py --target-sock /tmp/jam_target.sock \
  -d examples/0.7.2/no_forks
```

## Dependencies

- SBCL (Steel Bank Common Lisp)
- Rust toolchain (for crypto FFI)
- `ark-vrf` v0.1.0 (pinned in Cargo.lock)
- Python 3 + `jam_types` (`pip install git+https://github.com/davxy/jam-types-py.git`)
  for minifuzz
